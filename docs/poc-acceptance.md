# DHub V0 PoC 验收场景

## 启动与验收顺序

1. 准备一组可定位章节的合成 Markdown 及其元数据、两个小型示例 Repo 和可检索的调用关系。接入实际模型与只读工具，使用与项目模式相同的 Agent、报告和 Trace 契约。
2. 在网页提交下列案例。运行时检查角色和工具事件，结束后按证据链接逐项核对报告。
3. 接入可用的 Confluence 导出和项目仓库的固定提交，用同样步骤复核至少一条真实历史需求。真实项目的引用和依赖能力以联调结果为准。

## 主演示案例

**需求** “Mandatory outbound campaigns should no longer bypass the frequency cap, even when Allow mandate campaign override is enabled.”

FD2 Decisioning Process 截图给出了 P5 Step 18 的文档锚点。页面描述在相关 Global Setting 启用时，Mandatory Campaign 可以绕过 Frequency Cap。新需求限定 Outbound，适用范围和当前实现由调查确认。用下面的合成资料建立可判定的验收环境。

| 合成资料 | 验收用内容 |
| --- | --- |
| `DEMO-FD2` 决策过程页 | 在 P5 Step 18 给出豁免条件和配置引用。另有设置页令调查可以核实 Frequency Cap 和 Quiet Time 的配置位置 |
| `fixture-decision` | Frequency Cap 分支和相关配置。放入调用共享函数的 Inbound 与 Outbound 入口，放入可读取的已有测试断言 |
| `fixture-channel` | Outbound 消费筛选后候选集合的代码或接口契约，用于核对下游行为影响。关系由已读证据建立 |
| 调查工具 | Markdown 与代码能实际搜索和阅读，能在示例索引内查询共享函数的调用关系。按需要生成可供 `codegraph_read_result` 继续读取的结果 |

### 预期报告

- 定位 **P5 Step 18 Frequency Cap** 和 Mandatory Campaign 豁免。引用已读的原文章节，并说明拟议需求与该范围内的旧规则之间的差异。
- 引用函数分支和两个入口的代码位置。把共享逻辑导致的 Inbound 风险写成隔离验证，保留用户限定的 Outbound 范围。
- 找到配置读取或相关设置页。评估豁免配置的适用语义，基于证据判断 Quiet Time 是否需要额外验证。
- 在存在证据时，把 Delivery 表达为候选集或推送结果可能变化。将实现变更、配置检查和间接行为影响写入对应影响项。
- 定位已有测试断言，列出应补或调整的回归场景，并给出明确覆盖范围。

下表是此合成场景的 **Frequency Cap 环节**预期，代表输入条件与需求预期。整条 Decision Process 的推送结果还受到其他规则影响。

| 场景 | 当前示例行为 | 拟议行为 |
| --- | --- | --- |
| Outbound Mandatory，Override 开启，超过上限 | 通过 | 拦截 |
| Outbound Mandatory，Override 关闭，超过上限 | 拦截 | 拦截 |
| Outbound Mandatory，未超过上限 | 通过 | 通过 |
| Outbound Marketing，超过上限 | 拦截 | 拦截 |
| Inbound Mandatory，Override 开启，超过上限 | 通过 | 通过 |

### 预期 Trace

主 Agent 的任务下可以看到业务调查和代码调查。支持结论的文档和代码分别能回指到 `read_document` 和 `read_file` 等实际调用。页面可以看到搜索、代码图查询及相关的开始和结束状态。若在示例索引上测试了 CodeGraph 长结果，可从 Trace 证实 `codegraph_read_result` 沿用原 `result_id`，并可对比两个窗口。离线样例的计划随初始、Domain 后、Code 后和补查后共四个阶段更新。用 **Previous Version** 和 **Next Version** 核对 Code 后新增的两项补查与调整原因。刷新页面后仍能回到同一次运行、计划及证据。

## 扩展验收

| 场景 | 操作 | 通过条件 |
| --- | --- | --- |
| 跨 FD 规则差异 | 加入一个适用范围重叠但描述不同、无明确覆盖说明的后续 FD 合成页面 | 报告列出两份原文及差异，展示各自范围并保留适用性待确认。当前代码表现单独引用 |
| 项目资料不可用 | 使某个 Repo 或 CodeGraph 索引不可用，再提交主演示案例 | 能看到真实的不可用状态与理由。仍展示可核对的业务证据或已读源码，无法确认的依赖标为待核实 |
| 搜索零命中 | 对目录或代码执行一个无结果的查询 | 事件显示工具成功和 0 命中，报告如实说明调查范围及剩余问题 |
| 模糊需求 | 输入「调整 Frequency Cap」后再输入空白 | 合法输入列出缺失的作用对象或期望行为，空白输入给出可读的校验错误 |
| 工具超时 | 让一个工具超过运行限制 | Trace 对应行显示超时，运行进入可解释的部分完成或失败，已有事件能够回看 |
| 直接答复和隐式规划 | 先聊通用话题，再问需要一次查证的 DHub 规则 | 通用问题直接显示回复。查证开始后能在回复前看到调查步骤 |
| 中途启用显式计划 | 问 Inbound 和 Outbound 的频控差异，让首轮业务资料暴露 FD 差异 | 同一次请求内先显示业务调查，再显示计划和代码补查。修订保留已取得的证据，并显示新任务和原因 |
| 有待核实的计划任务 | 让模型在仍有开放任务时尝试交付终稿 | Main 可补查或补记原因。仍无足够证据的任务最终标为待核实，报告或回复中有可读说明 |
| 运行中刷新 | 在调查期间刷新页面，之后回看报告、计划和 Trace | 恢复同一运行，按序显示调用和计划版本，报告证据可定位对应工具 |

## 项目资料上的评估

由 BA 或 Developer 标注真实历史需求的关键文档、规则和例外、Process Step、代码模块及风险。尽量使用需求开发前的 Confluence 和仓库快照做回测。若历史快照缺失，记录所用资料状态和人工标注基准。

记录命中率与遗漏，分别看关键文档、规则和例外的召回，以及流程和代码影响的精确率与召回。抽查引用的页版本、章节、文件行和断言，核对已确认结论能否由这些证据推出。另记冲突检出、工具调用数、延迟和无证据结论。可先用同组案例比较关键词及目录基线与后续混合检索，再决定 V1 的检索投入。
